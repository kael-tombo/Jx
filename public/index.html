The missing front door to Java.

A proposed command-line tool for Java, in the spirit of Cargo, uv and npm. It would manage the JDK and dependencies from Maven Central, then build, test, run and package the project from one manifest. The goal is for jx run to work the same for plain Java, Spring Boot, Quarkus, Vert.x and Jakarta EE.

Starting a Java project takes too many decisions.

Today a new Java project starts with a JDK to pin, a build tool to choose and a wrapper command to remember. Maven often means pom.xml and ./mvnw. Gradle often means build.gradle and ./gradlew run. Spring Boot, Quarkus, Vert.x and Jakarta EE each add setup of their own.

Each tool is good at its job. Together they are a lot to learn before the first line runs.

Cargo, uv and npm each give their ecosystem one tool and one path. Java still asks you to assemble yours.

What smooth means.

Five properties the design is judged against.

One tool, one file.

A project has one manifest and one lockfile. The JDK pin, dependencies and build settings live together.

Minutes to first success.

The target is five minutes from nothing installed to a running program. We will measure it and publish the method.

Fast feedback.

Builds will skip work that did not change. Timings will come with the machine and project beside them.

Errors that tell you the fix.

A failure will name what happened, where it happened and the next command to try.

One default path.

Most projects will not need a build script. When they do, the manifest will leave room for one.

How it works.

Toolchain pins the JDK. Resolver reads Maven Central and writes the lockfile. Build engine runs javac and JUnit. Packager writes a jar, a distribution and an optional runtime image.

One command for every stack.

The destination is one command vocabulary for Java. The same jx run would work whether the project is plain Java or a framework. Cargo, uv and npm each provide one for their ecosystem. V1 covers plain Java only; framework adapters come later.

Target behaviour only. None of these adapters exists yet.
Stack What jx would do Status
Plain Java Compile and run a main class. Planned for V1
Kotlin and Scala Use the same flow with their compilers. After V1
Vert.x Start the application with the same command set. After V1
Spring Boot, Micronaut, Quarkus Start the application; reload is delegated to each framework. After V1
Jakarta EE Provision an application server for Jakarta EE (formerly Java EE). After V1

The same jx run is the goal in every row. No framework adapter is scheduled yet.

Works with Maven and Gradle.

Four levels are planned for V1. Gradle support covers a declarative subset of its build model.

Planned interop. None of these modes runs yet.
Level What it means Status
Export Write a Maven or Gradle build from the jx manifest. Planned for V1
Import Read an existing Maven or Gradle project into a jx manifest. Planned for V1
Compatibility mode Use the existing build files while jx supplies the toolchain and commands. Planned for V1
Delegate mode Call Maven or Gradle for the build. Planned for V1

Export is the exit: a project can leave with a build file it already understands. Maven plugins are not run natively in V1; delegate mode calls Maven or Gradle, and a plugin host is planned.

Principles and non-goals.

  • One tool. One manifest, one lockfile, one command set.
  • Smooth beats complete. Protect the shortest path to a running program.
  • Errors say what to do next. A message names the cause and a way forward.
  • Reuse the ecosystem. Maven Central stays. An export always offers a way out.
  • Fast by default. No JVM starts unless it is needed. Speed claims wait for measurements.
  • Never silent about risk. Conflicts, changed checksums and unsupported POM features stay visible.

Not before 1.0

  • Not a deployment tool.
  • Not a replacement for Maven Central.
  • No plugin ecosystem of its own.
  • No telemetry in V1.

Common questions.

Can I use it today?

No. There is no release, and the V1 plan is public.

Does it replace Maven or Gradle?

No. It reuses Maven Central. Import, export and delegate modes are planned.

Why Rust?

Rust starts without a JVM, and no JVM is needed to install JDKs. The JVM-side pieces stay in Java.

What about Spring Boot, Quarkus and the rest?

Spring Boot, Quarkus, Vert.x and Jakarta EE are planned as adapters after V1. V1 covers plain Java. The destination is the same jx run command for each.

Will it run my Maven plugins?

Not natively in V1. Delegate mode calls Maven or Gradle. A plugin host is planned.

Is it official or from Oracle?

No. It is independent.

How is it different from JBang, Amper and jot?

Each solves part of the problem. jx aims at one workflow. We are evaluating reuse and collaboration.

What about containers and production?

Daemonless images are post-V1. The V1 plan does not cover deployment.
