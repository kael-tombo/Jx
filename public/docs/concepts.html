Concepts

The manifest, lockfile, resolver and conflict policy as implemented in V1. Release binaries are pending.

This page describes V1 behaviour. The schema is validated by the same parser every command uses.

Manifest

A project has one manifest, project.toml. It names the project, pins a JDK and records dependencies. It also holds the entry point for jx run.

Illustrative manifest. Field names match V1. 
[project]
name = "hello"
version = "<version>"
jdk = "<version>"

[dependencies]
guava = "com.google.guava:guava:<version>"

[run]
main = "app.Main"

Dependency keys are local aliases. Values are Maven coordinates: group, artifact, and a version or a placeholder for one. The rules for ranges, overrides and platforms are recorded in the repository's manifest reference.

Lockfile

The lockfile, jx.lock, records the exact artifacts a build resolved. It is written by jx, not by hand. It is meant to make a build on another machine select the same versions.

Each entry carries a checksum. A changed checksum is a hard error, not a warning. A lockfile that silently accepts a different artifact is worse than no lockfile.

Resolver

The resolver reads POM metadata from Maven Central and builds a dependency graph. It applies the conflict policy, then writes the lockfile. jx tree and jx why explain the result.

Resolution is native to jx. Maven and Gradle are not required to resolve a graph.

Conflict policy

When two dependencies ask for different versions, the policy is:

  • Within one major version, choose the highest compatible version.
  • Across majors, stop with a hard error. The project must choose.

This is the implemented policy. It favours a visible failure over a silent downgrade. Every replacement is named in the resolution report.

Read the glossary entries for resolver and lockfile.

What can change

Repository configuration, mirrors and credential storage are documented in the repository. The manifest schema and lockfile format are V1; further changes are recorded as decision records.
