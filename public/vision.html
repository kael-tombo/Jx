Vision and principles.

Why jx exists, what smooth Java development means, and what the project does not claim to match.

Why this exists

A new Java project starts with a build system, a JDK manager, a packaging tool and a way to run one file. Each choice is reasonable. Made together, they are a wall between a person and a first program.

Cargo, uv and npm each give their ecosystem one front door. You learn one manifest, one command set and one place to look when something fails. Java has excellent tools, but no single front door.

jx is that door for plain Java. It puts one manifest and one command set over the JDK, Maven Central, javac, Maven, Gradle and the tools already on the machine, composing them rather than replacing them; from that one file it builds, tests, runs and packages the project. The destination is one run command: jx run for plain Java, Spring Boot, Quarkus, Vert.x and Jakarta EE. It is written in Rust and builds as one binary. V1 is implemented; no tagged release exists yet.

A platform tool, not a runtime

Two arguments are often made together: Java needs one tool for the everyday workflow, and the JRE is larger than it needs to be. They point at different layers. jx is aimed at the first: one manifest, one JDK pin, one command set, dependencies from Maven Central.

It does not add a runtime to every project or ask the JDK to ship more. It installs the JDK a project pins and reuses it. The optional runtime image uses the JDK's own jlink as packaging for a deployment, not as a change to what the JDK ships.

The same rule applies inside the workflow. jx is not a new package manager, build tool or script runner. It is the layer that composes the JDK, Maven Central, javac, JUnit, Maven, Gradle and the platform's installers. If a tool already owns the job, jx calls it. JBang and Chocolatey are adapter targets; neither is wired in V1.

jlink can trim a runtime after it exists. It does not give a project a manifest, a resolver or a run command. A platform tool can provide those without changing what the JDK ships. jx is independent; it is not an official Java tool and does not speak for the platform.

What smooth means

Smooth is not a feeling in a launch post. It is five properties that can be tested.

One tool, one file

A project has one manifest and one lockfile. The JDK pin, dependencies and build settings live together. A second file exists only to pin exact versions for another machine. The same jx run should work whether the project is plain Java or a framework.

Minutes to first success

The target is five minutes from a machine with nothing installed to a running program. The measurement will name the machine, the network and the method. Until then, the number is a target, not a result.

Fast feedback

Builds fingerprint their inputs and skip work that did not change. When timings are published, they will name the machine and project that produced them.

Errors that tell you the fix

A failure should name what happened, where it happened and the next command to try. An error that only says a file is missing has not finished its job.

One default path

Most projects will not need a build script. When they do, the manifest will leave room for one. The default path should be enough to start, not a cage.

Principles

  1. One tool. One manifest, one lockfile, one command set. Fewer moving parts in the first five minutes.
  2. Smooth beats complete. A smaller workflow that works end to end beats a larger one that is nearly done.
  3. Errors say what to do next. Every message names a cause and a next step. Silence is a bug.
  4. Sit on top of the ecosystem and offer an exit. The JDK, Maven Central, Maven, Gradle, JBang and the platform's installers keep their jobs; jx owns the path across them. Export is part of the design, not a rescue plan.
  5. Fast by default. No JVM starts unless it is needed. Speed is measured before it is claimed.
  6. Never silent about risk. Conflicts, changed checksums and unsupported POM features stay visible.

The smoothness tests

These are the tests V1 is judged by. They are recorded here so the project cannot move the goal after the fact.

  • A new user completes the hello flow with no Java installed. Exercised in the source tree; release pending
  • The same three commands work for a plain app, a Spring Boot app and a Quarkus app. After V1
  • A warm run after a one-line change is fast. Exercised in the source tree; timings pending
  • Every common error suggests a next step. Covered by the repository tests
  • A project can leave through export without lock-in. Covered by the repository tests

What jx will not match

Saying what a tool will not do is part of the design. These limits are deliberate.

Package management

OS installs stay with Chocolatey, Homebrew, Scoop or the platform's installer. jx is not a package manager.

Plugin ecosystems

Maven's plugin ecosystem is broad and old. jx does not match it in V1. Delegated builds call Maven or Gradle, so existing plugins run there; a plugin host is planned for later.

Versioning without SemVer

Java dependencies do not follow SemVer. jx uses compatibility ranges and a conflict policy. It cannot make version numbers mean something they do not.

Maturity

Cargo and uv have years of use and many edge cases behind them. jx starts at zero. The comparison is about shape, not experience.

The JRE's size

jx is a workflow tool, not a new JDK. It does not change what the JDK ships. An optional runtime image may be smaller because it uses the JDK's own jlink to assemble a deployment runtime; that is packaging, not a fix for the JRE's size.

The scope rule

Protect the five-minute happy path first. Widen coverage second.

A feature that does not help a new project reach a running program waits. That rule is easier to state than to keep. It is written here so the project can be held to it.
