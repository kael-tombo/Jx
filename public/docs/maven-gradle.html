Maven and Gradle

How jx works with existing Maven and Gradle projects: export, import and delegated builds.

Export, import and delegated builds are implemented in V1. Delegated builds cover the build, test and clean lifecycle; jx does not read the delegate's dependency graph.

Position

jx does not replace Maven or Gradle. It reuses Maven Central and keeps the existing build tools reachable. V1 has three levels of contact with them.

The destination is everyday work through commands such as jx run. Maven and Gradle stay available when a project needs them.

The interop modes

The interop levels implemented in V1.
Mode What it does Status
Export Write a Maven or Gradle build from the jx manifest. Implemented
Import Read an existing Maven or Gradle project into a jx manifest. Implemented
Delegated builds Run the project's own Maven or Gradle build for build, test and clean, with jx supplying the pinned JDK and command surface. Implemented

Import also accepts a Java-only, single-module jot.toml with its libs.versions.toml catalog and [processors]. That is a migration path beside the Maven and Gradle modes, not a third delegated build.

Import is the entrance. Export is the exit.

Gradle coverage

Gradle support covers a declarative subset of the build model. Projects outside that subset can use delegated builds, where Gradle performs the build and jx supplies the pinned JDK and command surface.

The subset is defined in ADR 0011 and documented in the repository, with the cases it cannot express named in public.

Maven plugins

Maven plugins are not run natively in V1. Delegated builds call Maven or Gradle, so an existing plugin setup can still run there. A plugin host is planned for later.

The exit

Export is the promise that a project can leave. A jx project can become a Maven or Gradle project with a build file those tools understand. A one-way conversion would be lock-in, and lock-in is a non-goal.

See the commands for import and export, or the concepts behind the manifest.
