The missing front door to Java.

A command-line tool for Java, in the spirit of Cargo, uv and npm. It puts one manifest and one command set over the JDK, Maven Central and the tools already on your machine, composing them rather than replacing them. It builds, tests, runs and packages from that one file. The goal is for jx run to work the same for plain Java, Spring Boot, Quarkus, Vert.x and Jakarta EE.

Starting a Java project takes too many decisions.

Today a new Java project starts with a JDK to pin, a build tool to choose and a wrapper command to remember. Maven often means pom.xml and ./mvnw. Gradle often means build.gradle and ./gradlew run. Spring Boot, Quarkus, Vert.x and Jakarta EE each add setup of their own.

Each tool is good at its job. Together they are a lot to learn before the first line runs. jx is not another tool to learn in place of them; it is a path across them.

Cargo, uv and npm each give their ecosystem one tool and one path. Java still asks you to assemble yours.

A front door, not a new runtime.

The case for a Cargo-like tool is not a case for a larger Java. jx does not bundle a JRE into every project, vendor dependencies into the repository, or ask the JDK to include more.

It installs the JDK a project pins and reuses it from a local store. Libraries still come from Maven Central. An optional runtime image built with the JDK's own jlink ships as packaging for a deployment. jlink can trim a runtime after it exists; it does not provide a manifest, a resolver or a command set.

It is also not a replacement for the tools inside the workflow. The JDK, Maven Central, javac, JUnit, Maven, Gradle and the platform's installers keep their jobs; jx owns the path across them.

The goal is a shorter path, not a larger bundle.

What smooth means.

Five properties the design is judged against.

One tool, one file.

A project has one manifest and one lockfile. The JDK pin, dependencies and build settings live together.

Minutes to first success.

The target is five minutes from nothing installed to a running program. We will measure it and publish the method.

Fast feedback.

Builds skip work that did not change. Published timings will name the machine and project behind them.

Errors that tell you the fix.

A failure names what happened, where it happened and the next command to try.

One default path.

Most projects do not need a build script. When they do, the manifest can delegate to one.

How it works.

One binary, one orchestration layer, no daemon. A run reads the project, ensures the JDK, resolves the lock, compiles and starts; the tools underneath keep their jobs.

jx is not a replacement for the Java toolchain. It is the layer above it: one manifest and one command set over the JDK, Maven Central, javac, JUnit, Maven, Gradle and the platform's installers. A command reads the project state, then calls the engine or the tool that owns the work.

The reuse rule

Own the path, not the wheel.

jx owns the manifest, the lockfile, the command vocabulary and the conflict policy — the parts no single tool owns.

The tools keep their jobs: the JDK, Maven Central, javac, JUnit, Maven, Gradle, JBang and the platform installers.

JBang and Chocolatey are adapter targets, not wired in V1. The dashed nodes below mark what is planned.

Path of one jx run

  1. Read the project.

    project.toml names the JDK, dependencies and main class. jx.lock pins the artifacts. If the manifest is newer, jx re-locks or fails under --locked.

  2. Ensure the JDK.

    Toolchain resolves the pinned feature through Eclipse Temurin, verifies the archive's SHA-256 and reuses the install from ~/.jx/jdks.

  3. Get the artifacts.

    Resolver takes the lock fast path when it can. Cached jars are checked against the lockfile's checksums; misses are fetched from Maven Central.

  4. Compile.

    Build runs javac with the pinned JDK. Fingerprints skip a build when the sources, resources and classpath have not changed.

  5. Start.

    Run discovers or uses the pinned main class and starts it on the pinned JDK. jx test adds JUnit, jx package writes target/dist, and jx image adds the optional runtime.

One command for every stack.

The destination is one command vocabulary for Java. The same jx run is the goal whether the project is plain Java or a framework. Cargo, uv and npm each provide one for their ecosystem. V1 covers plain Java; framework adapters come later.

Works with Maven and Gradle.

V1 provides three levels of interop. Gradle support covers a declarative subset of its build model.

The interop modes implemented in V1.
Level What it means Status
Export Write a Maven or Gradle build from the jx manifest. Implemented
Import Read an existing Maven or Gradle project into a jx manifest. Implemented
Delegated builds Run the project's own Maven or Gradle build for build, test and clean, with jx supplying the pinned JDK and command surface. Implemented

Export is the exit: a project can leave with a build file it already understands. Maven plugins are not run natively in V1; delegated builds call Maven or Gradle, so existing plugins run there. A plugin host is planned.

V1 · Plain Java

Implemented

The whole path, one tool.

  • Toolchain. Pin a JDK feature; fetch Eclipse Temurin; verify SHA-256; reuse it from the local store.
  • Dependencies. Resolve from Maven Central with POMs, BOMs, overrides and a checksum-pinned lockfile.
  • Build and test. Run javac with fingerprints, copy resources, and launch JUnit on the test classpath.
  • Run and package. Discover the main class, write thin and fat jars, a dist tree and an optional runtime image.
  • Interop. Import Maven and Gradle; export Maven and Gradle; delegate build, test and clean to either tool.
  • Composition. Call the JDK, Maven Central, javac, JUnit, Maven and Gradle. jx owns the path; the tools keep their work.
  • Guardrails. Offline and locked modes, a doctor command, tree and why reports, and a visible conflict report.

After V1 · The same command

Unscheduled

One jx run across stacks.

  • Framework adapters. Spring Boot, Quarkus, Vert.x, Micronaut and Jakarta EE start with the same command.
  • Languages. Kotlin and Scala compilers join the same manifest and flow.
  • Tool adapters. JBang for scripts and single-file programs; Chocolatey, Homebrew and Scoop for OS installs. Evaluate each before wiring it.
  • Plugin host. A Maven plugin host sits beside the build engine.
  • Framework reload. Hot reload stays with each framework; jx does not reimplement it.

The destination is shared; no adapter is scheduled.

The boundary · Not in V1

Deliberate

A front door, not a takeover.

  • Not a runtime. No new JDK, no replacement JRE, no fix for the JRE's size.
  • Not a deployment tool. Images are packaging; shipping stays out of scope.
  • Not a registry. Maven Central stays the source; export is the exit.
  • Not a package manager. OS installs stay with Chocolatey, Homebrew, Scoop or the platform's own installer.
  • No new plugin ecosystem. Maven plugins stay Maven's; jx delegates or hosts them later.
  • No telemetry. V1 collects nothing.

These are scope decisions, not missing features.

Principles and non-goals.

  • One tool. One manifest, one lockfile, one command set.
  • Smooth beats complete. Protect the shortest path to a running program.
  • Errors say what to do next. A message names the cause and a way forward.
  • Sit on top of the ecosystem. The JDK, Maven Central, Maven, Gradle, JBang and the platform installers keep their jobs; jx owns the path across them. An export always offers a way out.
  • Fast by default. No JVM starts unless it is needed. Speed claims wait for measurements.
  • Never silent about risk. Conflicts, changed checksums and unsupported POM features stay visible.

Not before 1.0

  • Not a deployment tool.
  • Not a new JDK or a replacement JRE.
  • Not a fix for the JRE's size.
  • Not a replacement for Maven Central.
  • No plugin ecosystem of its own.
  • No telemetry in V1.

Common questions.

Can I use it today?

V1 is implemented, but no tagged release exists yet. Build from source for now; the installers will publish from the v1.0.0 tag.

Does it replace Maven or Gradle?

No. It reuses Maven Central. Import, export and delegated builds are implemented in V1.

Is jx another runtime, or a fix for the JRE's size?

No. It is a workflow tool. It installs the JDK a project pins and resolves libraries from Maven Central; it does not add a JRE to every project. An optional runtime image built with the JDK's own jlink is packaging for a deployment. jlink trims a runtime; it does not provide a manifest, a resolver or a run command. It is not a fix for the JRE's size.

Why Rust?

Rust starts without a JVM, and no JVM is needed to install JDKs. The JVM-side pieces stay in Java.

What about Spring Boot, Quarkus and the rest?

Spring Boot, Quarkus, Vert.x and Jakarta EE are planned as adapters after V1. V1 covers plain Java. The destination is the same jx run command for each.

Will it run my Maven plugins?

Not natively in V1. Delegated builds call Maven or Gradle, so existing plugins run there. A plugin host is planned.

Is it official or from Oracle?

No. It is independent.

How is it different from JBang, Amper and jot?

Each solves part of the problem. JBang runs scripts and single files; jx is aimed at the project workflow across the tools that already exist, not at replacing them. JBang is an adapter target, not wired yet.

What about containers and production?

Daemonless images are post-V1. The V1 plan does not cover deployment.
