# 0005. Packaging layout and runnable jar manifest

Date: 2026-10-31
Status: Accepted

## Context and problem

M5 turns compiled classes into something a user can run outside jx. The
project promises a Cargo/uv-style front door, not a new Maven repository
format. Packaging therefore has to be predictable, portable across operating
systems, and honest about what it does not do. The two obvious shapes are a
fat jar that contains every dependency, or a thin application jar next to a
directory of dependency jars.

Fat jars need shading decisions (duplicate classes, service files, signatures,
module descriptors) before they are trustworthy. Shipping a subtly broken
shaded jar is worse than shipping a transparent thin layout.

## Decision

`jx package` writes a **thin jar plus a dist directory**:

```text
target/dist/
  <name>-<version>.jar
  lib/
    com/google/guava/guava-33.7.2-jre.jar
    ...
```

* The application jar contains the project's compiled classes and main
  resources. It never contains dependency contents.
* Dependencies are copied below `lib/` using their group as a directory path,
  then `artifact-version[-classifier].jar`. This keeps two artifacts with the
  same file name from different groups from colliding.
* The manifest is generated by jx:
  * `Main-Class` when the manifest pins one or discovery finds exactly one;
  * `Class-Path` as space-separated **relative** `lib/...jar` entries;
  * header lines are wrapped to the jar format's 72-byte limit.
* A library with no main class still gets a jar, without `Main-Class`.
  Ambiguous main classes fail loudly instead of being resolved arbitrarily.
* `target/dist` is replaced from scratch on every package, so removed
  dependencies and stale files cannot survive. Jar entries are written in
  deterministic sorted order with deflate compression.
* All path-derived names are validated as single safe components. Versions,
  classifier names and project versions containing path separators,
  whitespace or control characters are rejected before anything is written.

The command is `jx package`; `jx build` remains compile-only.

## Options considered

* **Fat/shaded jar by default** — convenient, but duplicate classes, service
  loader files, signatures and `module-info.class` need careful merging.
  Deferred until those rules are implemented and tested.
* **Absolute paths in `Class-Path`** — makes `java -jar` work on the machine
  that built it, but breaks as soon as `target/` moves or is copied. Not
  chosen.
* **No dist, only a jar** — a dependency-bearing application would not run
  without an external classpath; the package would not meet the
  five-minute-happy-path promise.
* **Maven's `target/<finalName>.jar` plus `target/lib`** — workable, but
  mixing generated files with intermediate build output makes cleanup and
  copying less obvious. A dedicated `target/dist` is the deployable unit.

## Consequences

* Moving or archiving `target/dist` keeps the application runnable with
  `java -jar target/dist/<name>-<version>.jar`; the `lib/` tree must travel
  with it.
* Opt-in fat jars were added later with explicit merge rules in
  [ADR 0006](0006-fat-jar-merge-rules.md). No jar signing, relocation-aware
  shading, jlink image, native launcher or `export maven` output yet; those
  remain M5/M6/M7 work and are listed in `docs/KNOWN_LIMITATIONS.md`.
* Packaging reuses the normal compile and lock fast paths: dependencies come
  from verified cache entries and no network is needed when the lock and
  cache are complete.
